# ดิกชันนารีคำของโปรแกรม (Wording glossary)

หนึ่งความหมาย = หนึ่งคำ สำหรับ **ข้อความที่ผู้ใช้เห็น** (ป้าย ปุ่ม tooltip ข้อความแจ้งเตือน
และข้อความใน Log) — ไม่บังคับกับคอมเมนต์/docstring หรือคีย์ config ในโค้ด

ไฟล์นี้เป็น "แหล่งความจริงเดียว": ตัวตรวจ `tools/_wordterms_verify.py` **อ่านตารางข้างล่าง
นี้ไปบังคับใช้จริง** — แก้ตาราง = แก้กฎทันที โดยไม่ต้องแก้โค้ดตัวตรวจ
(ตัวแก้คำ `tools/_apply_wording.py` ใช้ตัวจำแนกกลางตัวเดียวกัน จึงคุมเรื่องนี้ทั้งระบบ)

## ตารางคำ (แก้ที่นี่ที่เดียว)

| ความหมาย | ใช้คำนี้ | ห้ามใช้ | เหตุผล |
|---|---|---|---|
| คุกกี้ที่ใช้ล็อกอิน | `Cookie` | `cookie`, `คุกกี้`, `โทเค็น`, `โทเคน` | ตรงกับปุ่มในโปรแกรม (`🍪 ล้าง Cookie ทั้งหมด`) และโฟลเดอร์ `sf_cookies` |
| เซสชันของเว็บ | `เซสชัน` | `session` | ข้อความไทยอ่านลื่นกว่า และเดิมใช้ปนกัน 2 แบบ |
| การเข้าสู่ระบบ | `ล็อกอิน` | `เข้าสู่ระบบ`, `ลงชื่อเข้าใช้` | ใช้มามากที่สุด (93 จุด) และสั้นกว่า |
| คีย์เวิร์ดที่ส่งเข้าเว็บ | `คีย์เวิร์ด` | `keyword` | ภาษาไทยทั้งโปรแกรม |
| รหัส 8 ตัวที่กรอก | `โค้ด` | `รหัสคีย์`, `รหัสคีย์เวิร์ด` | แยกจาก `รหัสผ่าน` ชัดเจน ไม่กำกวม |
| รหัสผ่านของบัญชี | `รหัสผ่าน` | `พาสเวิร์ด`, `password` | ภาษาไทยทั้งโปรแกรม |
| ชื่อผู้ใช้ในเกม | `ไอดี` | `username`, `ยูสเซอร์` | ผู้ใช้เรียก "ไอดี" (แถวไอดี) |
| แถวบัญชีที่เก็บรหัสผ่าน | `บัญชี` | `account` | แยกจาก "ไอดี" ที่เป็นชื่อในเกม |
| ความเร็วของบอท | `สปีด` | `ความเร็ว` | ใช้คู่กับ `เต็มสปีด` ได้ |
| งานที่รันคู่ขนานพร้อมกัน | `จำนวนพร้อมกัน` | `งานพร้อมกัน`, `thread`, `เธรด` | ตรงกับป้ายในหน้าตั้งค่า |
| ของที่ได้จากคีย์ (รายชิ้น) | `ไอเทม` | `รางวัล` | รายชิ้นเรียกว่าไอเทม |
| กลุ่มของที่ได้จากคีย์ (หมวดใน Log) | `ของที่ได้รับ` | — | เป็นชื่อหมวด/ปุ่มกรอง ไม่ใช่ตัวไอเทม |
| การอัปเดตโปรแกรม | `อัปเดต` | `อัพเดต`, `อัพเดท`, `อัปเดท` | สะกดตรงกันทุกจุด |
| หน้าตั้งค่าของโปรแกรม (คำนาม) | `การตั้งค่า` | — | ใช้เป็นคำนาม เช่น `การตั้งค่าบอท` |
| การตั้งค่า (คำกริยา) | `ตั้งค่า` | — | ใช้เป็นกริยา เช่น `ยังไม่ได้ตั้งค่า URL` |

> คำอังกฤษในคอลัมน์ "ห้ามใช้" ต้องตรง **ตัวพิมพ์เล็ก** ตามที่เขียนไว้ — `Cookie` และ
> `Keyword` (ชื่อหน้าเว็บ) จึงไม่ถือว่าผิด แต่ `cookie` / `keyword` ในข้อความผู้ใช้เห็น
> ถือว่าผิด (ต้องเปลี่ยนเป็นรูปที่กำหนด)

## คำที่ไม่แก้ ไม่รายงาน (ชื่อเฉพาะ / ข้อความจากภายนอก)

- `SFKeyword` — ชื่อโปรแกรม
- `หน้า Keyword`, `ไฟล์ Keyword`, `หน้า Login`, `Logout` — ชื่อหน้า/ไฟล์ของเว็บเกม
  (ต้องตรงกับหน้าเว็บจริง)
- `รับรางวัล` — อยู่ในรายการเดียวกับข้อความที่ใช้เทียบผลลัพธ์จากเว็บ
- `Message ID`, `ID=` — ศัพท์เทคนิคของ Discord (ไม่ใช่ "ไอดี" ของผู้ใช้)
- ข้อความที่ใช้ "เทียบ" กับคำตอบของเว็บ (เช่น `LOCKED_HINTS`, `KEYWORD_ERROR_PATTERNS`,
  `_REASON_CATEGORY_PATTERNS`, `รับรางวัลแล้ว`, `คุณได้รับ`) — ห้ามแปล/แก้ เพราะใช้ตรวจ
  ผลลัพธ์จากเว็บโดยตรง ตัวจำแนกกลางหาให้เองจากโครงสร้างโค้ด (ดู `detect_nodes`)
- `Discord`, `Webhook`, `UpdatePanel`, `sf_cookies` ฯลฯ — ชื่อบริการ/เทคโนโลยี/ไฟล์
- คีย์ config, ชื่อตัวแปร, ค่าที่เก็บลงไฟล์ — ไม่นับเป็นข้อความผู้ใช้เห็น

## วิธีใช้ / วิธีตรวจ

```bash
# 1) ดูสถิติคำที่ใช้จริงทั้งโปรแกรม (วินิจฉัย ไม่มีผลผ่าน/ไม่ผ่าน)
venv/Scripts/python.exe -X utf8 tools/_wording_audit.py

# 2) ดูว่าจะแก้จุดไหน (ไม่เขียนไฟล์) แล้วรันแก้จริง
venv/Scripts/python.exe -X utf8 tools/_apply_wording.py
venv/Scripts/python.exe -X utf8 tools/_apply_wording.py --write

# 3) ตรวจว่าตรงตามดิกชันนารีแล้ว (อยู่ในชุด harness ที่ build เรียกเป็นด่านเอง)
venv/Scripts/python.exe -X utf8 tools/_wordterms_verify.py
```

ตัวตรวจจะ **แดง** ถ้าพบคำในคอลัมน์ "ห้ามใช้" ในข้อความที่ผู้ใช้เห็น (ยกเว้นข้อความที่ใช้
เทียบกับเว็บและคำที่ไม่แก้ข้างบน) และมี negative control 2 ตัวพิสูจน์ว่าตัวจับทำงานจริง:
จับได้เมื่อควรจับ (`คุกกี้`) และไม่จับเมื่อไม่ควร (`Cookie`, `sf_cookies`, `ไฟล์ Keyword`)

## รูปแบบบรรทัด Log (บังคับ — มีด่านตรวจอัตโนมัติ)

> หมายเหตุ: หัวข้อนี้ **ไม่ใช่ตารางคำ** (ตารางคำคือหัวข้อข้างบนที่ตัวตรวจอ่านไปบังคับใช้)
> เพราะเป็นกฎ "รูปแบบบรรทัด" ซึ่งคุมด้วยด่านแยก ไม่ใช่คำศัพท์

- **สัญลักษณ์หัวบรรทัด** ใช้ชุดเดียว: ✓ สำเร็จ · ! เตือน · ✗ ล้มเหลว · • ข้อมูล
  \- สัญลักษณ์ชุดเก่าที่ห้ามกลับมาใช้: ⚠ ✔ ❌ ℹ ⏭ 🔒 (ด่าน S2 สแกนทั้ง self.log และ self._inv_log)
- **สัญลักษณ์โครงสร้าง** ที่คงไว้: ■ เริ่ม/สรุป/ปิดเซสชัน/รวมเวลา · ▶ เริ่มงาน ·
  ①–⑨ ขั้นตอน · 📥 📤 🗑 โหมดฝาก/เบิก/ลบ · 🎁 ของที่ได้รับ · 💾 🔄 → ⏹
- **บรรทัดขั้นตอน (① ② …)**: ขั้นละบรรทัด และขึ้นจอ **ทันทีที่จบขั้นนั้น** (log
  เรียลไทม์) — ห้ามยุบทุกขั้นกลับไปรวมเป็นบรรทัดเดียวแล้วค่อย log ตอนจบ และ
  ห้ามปิดท้ายด้วยยอดรวม `Σ` (เวลารวมมีบรรทัดของตัวเองอยู่แล้ว) ⇒ รูปแบบเดิมถูก
  ถอดออกจาก renderer แล้ว พร้อมโค้ดตัดบรรทัดพิเศษที่เคยบังคับ "ขั้นตอนละบรรทัด"
  (ด่าน S1–S7 ใน `tools/_logsteps_verify.py` · ST1–ST6b ใน `tools/_step_realtime_verify.py`)
- **ข้อความแจ้งเตือนหลายบรรทัด**: หัว 1 บรรทัด (`• <หัวข้อ>: <บรรทัดแรก>`) แล้วเยื้อง
  4 ช่อง บรรทัดละรายการ — **ห้ามยุบเป็นบรรทัดเดียวแล้วต่อท้าย “(อีก N บรรทัด)”**
  (เจอจริง: อ่านแล้วงง ตัวเลข สำเร็จ/ไม่สำเร็จ/เวลารวม หายไปจาก Log และดูเหมือน
  โปรแกรมจะพิมพ์บรรทัดตามมาอีก) — เกิน 6 บรรทัดค่อยยุบเป็น `… และอีก N บรรทัด`
  ขีดจำกัดอยู่ที่ `AppDialogsMixin._NOTICE_MAX_EXTRA_LINES` จุดเดียว
- **ข้อความ 'เสร็จสิ้น' ต้องไม่ซ้ำ Log**: popup แสดงข้อความเต็มได้ แต่ Log เขียนแค่
  **หัวบรรทัดเดียว** ผ่าน `_notify_done(..., log_message=<หัวบรรทัด>)` — เพราะตัวเลขสรุป/
  รายไอดี/เวลารวม ถูก log ไปแล้วก่อนหน้า (เจอจริง: เขียนซ้ำสองรอบติดกัน) ทุกจุดเรียก
  ต้องระบุ `log_message` เอง ⇒ ไม่ต้องพึ่ง "(อีก N บรรทัด)" อีก
  ถ้างานนั้นมี **บรรทัดสรุปของตัวเอง**อยู่แล้ว (เช่นโหมดรับไอเทมฟรี:
  `• [อัตโนมัติ 00:05] รับไอเทมฟรีเสร็จแล้ว  สำเร็จ 20/23 บัญชี · ไม่สำเร็จ 3`)
  ให้ส่ง `log_message=""` = **ไม่เขียน Log เลย** — และบรรทัดสรุปนั้นต้องมีจำนวนที่
  ไม่สำเร็จครบ (ห้ามตัดข้อมูลทิ้งเพื่อให้สั้น) (ด่าน L13a–L13e)
- **เส้นคั่นและหัวบล็อก**: ห้ามเส้นคั่นทุกแบบ (การขีดยาว) และห้ามหัวบล็อกที่เป็นชื่อไอดีล้วน
  — ชื่อไอดีอยู่ในทุกบรรทัดอยู่แล้ว (ด่าน S7 + L1) ตัวบ่งชี้หัวข้อใช้หมวดสี ไม่ใช้ตัวอักษร
- **ตัวคั่นในบรรทัด**: ใช้ช่องว่างคู่ หรือ ` · ` ระหว่างตัวเลขสรุป — ห้ามใช้ขีดยาว
  (em dash) และ `--` คั่น (ด่าน L2 + L9b สแกนซอร์ส)
- **การอัปเดต**: ตรวจครั้งเดียวตอนเปิดโปรแกรม (ก่อนหน้าต่างหลักขึ้น) — ไม่มีตัวตรวจ
  เบื้องหลังและไม่มีบรรทัดอัปเดตระหว่างใช้งาน · ในหน้าต่างอัปเดตห้ามใช้ em dash คั่น
  (ด่าน L9b) · เลี่ยงคำเทคนิคอย่าง `SHA`/`PHPSESSID` ในบรรทัดที่ผู้ใช้เห็นบ่อย
  (เขียนเป็น `ไฟล์ไม่ผ่านการตรวจ` พร้อมเหตุในวงเล็บ) — ด่าน `tools/_updateflow_verify.py`
  คุมว่าการเช็คอัปเดตยังผูกกับการเปิดโปรแกรม · การตรวจไฟล์ก่อนติดตั้งยังอยู่ครบ
  (ขนาด + SHA-256 + ชนิดไฟล์) · และตัวระบบที่ถอดออกต้องไม่เหลือร่องรอยในโค้ด
- **ป้ายแรงค์ในบรรทัดส่งคีย์**: ใช้ข้อความเดียวกับช่องเลือกในแถวไอดี (`constants.RANK_LABEL`)
  ⇒ `(แรงค์ 1)` / `(แรงค์ 2)` / `(ไม่เลือก)` — ห้ามกลับไปใช้ `r1` / `r2` / `--`
  (ห้ามครอบด้วยวงเล็บเหลี่ยม `[ ]` เพราะกลไกดึงชื่อไอดีจะตีเป็นชื่อไอดีปลอม)
- **บรรทัด `· เลือก …` ต้องบอกค่าที่เลือกจริง** (ผู้ใช้ทัก 13 ก.ย. 2569: “`· เลือก แรงค์`
  เป็น `· เลือก แรงค์ 2` ให้ขึ้นตามแรงค์ที่เลือก หรือหน่วยตัวละครที่เลือก”)
  ⇒ แรงค์: ใช้คำจาก `constants.RANK_LABEL` (`แรงค์ 1` / `แรงค์ 2`) · หน่วย: `หน่วย <ชื่อ>`
  (`หน่วย DELTA`) ด้วยชื่อมาตรฐานจาก `UNIT_ALIASES` ไม่ใช่ข้อความดิบบนเว็บ
  - ห้ามขึ้นคำลอย ๆ ว่า `แรงค์` เฉย ๆ — แม้ป้ายบนเว็บจะเขียนแค่ `Rank` แต่โค้ดรู้ว่า
    เลือกแถวไหน จึงต้องพาค่านั้นออกมา (`via` = `rank:1` / `rank:2` / `unit:<ชื่อ>`)
  - ยังคงห้ามพ่วงรหัส/ที่มา: `SRL=19948` · `(จากชื่อบนเว็บ)`
  - ด่าน: `tools/_logclean_verify.py` L15
- **ป้ายแรงค์เป็น chip สี**: บรรทัดส่งคีย์ทา `(แรงค์ 2)` ด้วยพื้นสีทึบ (แรงค์ 1 ฟ้า ·
  แรงค์ 2 อำพัน · ไม่เลือก เทา) ให้เห็นด้วยหางตา — สีป้ายคงที่ ไม่ผูกกับสี log
  ที่ผู้ใช้ปรับ (ช่องตั้งค่าสี log แก้เฉพาะสีตัวอักษร) และห้ามเปลี่ยนตัวอักษรของ
  บรรทัดเพื่อทำ chip (chip คือ tag ไม่ใช่ข้อความ)
- **ห้ามเศษเทคนิคลงบรรทัดที่ผู้ใช้เห็น** (ผู้ใช้ทัก 13 ก.ย. 2569: “อยากตัดคำพวกนี้ออก
  จาก Log เช่น `(จากชื่อบนเว็บ) SRL=19948` และ `(PHPSESSID)`”) ⇒ ห้ามในบรรทัด log บนจอ
  - `key=value` ของรหัสภายใน: `SRL=19948` · `ID=<เลข>` · `ผู้ส่ง=…` · `เวลา=…`
  - วงเล็บที่บอก “ที่มา/กลไก” ของโปรแกรม: `(จากชื่อบนเว็บ)` · `(จากหน้าต่างดู/เลือกไอเทม)`
  - ชื่อคุกกี้/คีย์ภายใน: `(PHPSESSID)` — ให้เขียนเป็นไทย เช่น `• ล้างแคชคีย์ประจำวัน`
  เขียนเป็นไทยอ่านรู้เรื่องหรือตัดทิ้ง · รหัสที่จำเป็นต่อการแก้ปัญหาให้ลงไฟล์วินิจฉัย
  (`update_log.txt` · debug log) ไม่ใช่ log บนจอ · บรรทัดที่ลงไฟล์อย่างเดียว
  (เช่น `_update_log`) ไม่นับ · ด่าน: `tools/_logclean_verify.py` L14
- **ความยาว**: ต้องพอดีหนึ่งบรรทัดในช่อง Log — ข้อความยาวจากเว็บให้ย่อด้วย
  `short_log_reason` (เช่น "คีย์ไม่ถูกต้อง") แล้วเก็บข้อความเต็มไว้ใน debug log

- **เหตุผลต้องเป็นความจริง ห้ามเดา**: ทุกป้ายที่ผู้ใช้เห็น (log · สรุปจบรอบ · popup)
  ต้องมาจากข้อมูลที่รู้จริง — ถ้าอ่านผลไม่ได้ ให้บอกว่า **“เว็บไม่ยืนยันผล”**
  ห้ามฟันธงว่า "เคยใช้ไปแล้วหรือหมดอายุ" (เจอจริง 12 ก.ย. 2569: ข้อความนี้ทำให้
  คีย์ที่บัญชีอื่นยังรับได้ถูก *ข้ามทั้งชุด* พร้อมป้ายเท็จ)

## วงเล็บเหลี่ยมใน Log = ชื่อไอดีเท่านั้น

- `[ ]` สงวนไว้ให้ **ชื่อไอดีจริง** (ต้องมาจากตัวแปรเท่านั้น) — ห้ามใส่
  ข้อความคงที่/ป้ายของโปรแกรมลงในวงเล็บ เพราะตัวอ่าน log จะตีเป็นไอดี
  แล้วเกิด **ปุ่มกรอง/สีไอดีปลอม** ขึ้นบนแถวไอดี (เจอจริง: `[บัญชีที่ 23.]`,
  `! [ไอเทมฟรี] …`, `! [Watchdog] …`)
- แถวที่ยังไม่กรอกชื่อไอดี: เขียน `แถวที่ N` **ไม่ต้องครอบวงเล็บ**
- ป้ายของโปรแกรม: เขียนนำด้วยสัญลักษณ์หมวดแทนวงเล็บ เช่น
  `! ไอเทมฟรี · …` (เตือน) · `✗ {หัวเรื่อง}: {ข้อความ}` (ผิดพลาด)
- สัญลักษณ์หัวบรรทัดที่อนุญาต: `✓ ✗ ! • ⚠ ■` (+ สัญลักษณ์โครงสร้าง ▶ ⏹ 💾 🔄 → 📥 📤 🗑 ฯลฯ)
  `⚠` ใช้กับบรรทัดแจ้งเตือน เพื่อให้ตกหมวด `warn` และกดปุ่มกรอง "⚠ คำเตือน" เจอ
- **แถวไอดี (ปุ่มกรอง) ผูกกับตารางบัญชีเท่านั้น = ตารางคือแหล่งความจริงเดียว**
  ไอดีที่ออกจากตาราง (ล้างทั้งหมด / ลบแถว / โหลดชุดใหม่ทับ) ปุ่มกรองหายทันที
  **แม้ log เก่าจะยังมีบรรทัดของไอดีนั้นค้างอยู่** — ถ้าไอดีถูกใช้จริงอีกครั้ง
  บรรทัด log ใหม่จะพาปุ่มกรองกลับมาเอง (เจอจริง: ล็อกอิน 10 ไอดี → ล้างบัญชีทั้งหมด
  → แถวไอดียังโชว์ครบ)
- **บรรทัดสรุปวิธีล็อกอิน = บรรทัดเดียว** `ใช้ Cookie 10 (0.4วิ/บัญชี) · ล็อกอินใหม่ 0`
  จำนวน + เวลาเฉลี่ยของวิธีเดียวกันต้องอยู่ด้วยกัน (ฝั่งที่ 0 บัญชีไม่ต้องมีวงเล็บเวลา)
  — ห้ามแยกจำนวนกับเวลาเป็นคนละบรรทัด เพราะบรรทัดล่างจะดูลอย ๆ อ่านไม่จบ- **เวลาของทั้งเฟสใช้หน่วยเดียวกับเวลาต่อบัญชี** — ใต้ 1 นาทีขึ้น `0.3วิ` / `4.6วิ`
  (ไม่ใช่ `00:00`) ตั้งแต่ 1 นาทีขึ้นไปเป็น `01:12` และเกินชั่วโมงเป็น `01:02:05`
  — ล็อกด้วยด่าน `_speed_verify` T8 · เดิม `int()` ทิ้งทศนิยม ทำให้เฟสที่ใช้จริง
  0.3 วิ ขึ้น `00:00` ขัดกับบรรทัด `0.3วิ/บัญชี` ที่โชว์คู่กัน (ผู้ใช้ทัก 13 ก.ย. 2569)
- คำเรียกวิธีล็อกอินที่ผ่าน Cookie ใช้ **"ใช้ Cookie"** (ห้าม "Cookie เดิม" — ฟังแล้ว
  แปลก ผู้ใช้ทัก 13 ก.ย. 2569) และประโยคใน flow ใช้ "ใช้ Cookie ที่เคยบันทึก"
  / "เก็บ Cookie ที่มีอยู่ไว้ก่อน" · ล็อกด้วยด่าน `_speed_verify` T7

## เซสชัน / Cookie — "ล้าง Cookie ทั้งหมด" ต้องมีผลทุกแท็บ

- **คุกกี้/เซสชันของไอดีใช้ร่วมกันทุกฟีเจอร์** (คีย์เวิร์ด · รับไอเทมฟรี · ฝาก/เบิก)
  ต่อ 1 บัญชี — ไฟล์ `<md5>.http.json` ใน `sf_cookies` (อ่าน/เขียนจาก `core/http_flow.py`
  ที่เดียว) บวกเซสชันที่ค้างในหน่วยความจำของ store เดียวกัน (`_http_session_store`)
- **ปุ่ม `🍪 ล้าง Cookie ทั้งหมด` (แดชบอร์ด) ต้องเก็บกวาดครบ 3 ที่**
  ① ไฟล์คุกกี้ทุกบัญชี (`clear_all_cookie_files()` — ลบ `.tmp` ที่ค้างด้วย)
  ② เซสชันในหน่วยความจำของทุกแท็บ (`_drop_all_http_sessions()` ล้าง `self._sessions`
  + store + แคชผลล็อกอิน) ③ แคช PHPSESSID ของการดึงคีย์ประจำวัน (`clear_coupon_session_cache()`
  — คนละไฟล์ อยู่นอก `sf_cookies`) แล้วรีเซ็ต UI ให้ตรงความจริง (`_close_sessions_cleanup`)
  — เดิมลบแค่ไฟล์บนดิสก์ ⇒ กดล้างแล้วรัน ฝาก/เบิก หรือ รับไอเทมฟรี ยังใช้เซสชันเดิมต่อ
  (ผู้ใช้ทัก 13 ก.ย. 2569)
- **บรรทัด log ของปุ่มล้างแยกตามงาน — ห้ามยัดรวมบรรทัดเดียว** (ผู้ใช้ทัก 13 ก.ย. 2569
  "ล้างก็ส่วนล้าง ปิดก็ส่วนปิด อย่าเอาไปรวมกัน") ⇒ พิมพ์เฉพาะเรื่องที่เกิดขึ้นจริง
  คนละบรรทัด: `• ล้าง Cookie ทั้งหมดแล้ว N ไฟล์` · `• ปิดเซสชันในหน่วยความจำ N บัญชี` ·
  `• ล้างแคชคีย์ประจำวัน` (ไม่มีไฟล์/ไม่มีเซสชัน = ไม่พิมพ์บรรทัดนั้น · **ห้ามใส่ชื่อคุกกี้/โทเคนเทคนิคลงบรรทัดที่ผู้ใช้เห็น** — ผู้ใช้ทัก 13 ก.ย. 2569)
- **ปุ่ม ⛔ ปิดเซสชันทั้งหมด ต้องปิดจริงทั้ง 2 ที่** — ใช้ตัวเดียวกันกับปุ่มล้าง
  (`_close_sessions_everywhere`) เพราะเดิมเคลียร์แค่รายการบนแดชบอร์ด เซสชันของ
  ฝาก/เบิก/รับไอเทมฟรี ค้างต่อ ⇒ กดล้าง Cookie แล้วยังขึ้น "ปิดเซสชัน" อีกรอบ
  (ดูเหมือนปิดซ้ำ) · ตอนปิดโปรแกรมก็ใช้ตัวเดียวกัน และ **ไม่ใช้ ✗** กับกิจวัตรนี้
  (✗ = ตกเป็น ERROR ใน error_*.log ทั้งที่ไม่ใช่ความผิดพลาด)
- **ปุ่มห้ามเทาค้าง** — เกณฑ์ enable คือ "มีอะไรให้ล้างไหม" (`_has_cookie_or_session`)
  ต้องนับเซสชันในหน่วยความจำ + แคชคีย์ประจำวันด้วย ไม่ใช่ดูแค่ไฟล์ใน `sf_cookies`
  ด่าน: `tools/_clearcookie_verify.py` (C1–C6 พฤติกรรมจริง + C7 negative control ·
  C3f แยกบรรทัด · C8 ปุ่มปิดปิดจริง · C9 ตอนปิดโปรแกรม)


## Log ฝาก/เบิก — บอกหน่วยให้ชัด แยกเหตุผลจริง และเดินหน้าให้เห็นเป็นตัวเลข

- **บรรทัดสรุปท้ายรอบบอกหน่วยเสมอ** — ตัวเลขบัญชีเขียนกำกับ `บัญชี` และยอดชิ้น
  เขียน `ชิ้น` (เช่น `ทำครบ 0 บัญชี · พลาดบางส่วน 1 บัญชี` คู่กับ `■ รวมฝาก 1900/1901 ชิ้น`)
  — เดิมขึ้น `สำเร็จ 0 · พลาดบางส่วน 1` ทั้งที่ฝากได้ 1900/1901 ชิ้น ผู้ใช้อ่านแล้ว
  เข้าใจว่าไม่ได้อะไรเลย (ทัก 13 ก.ย. 2569)
- **หน่วยของจำนวน "ไอเทม" ใช้ `ชิ้น` ทั้งโปรเจกต์** — `ดึงรายการไอเทม: พบ 63 ชิ้น` ·
  `🎁 … ได้รับ 3 ชิ้น` · `■ รวมฝาก 1900/1901 ชิ้น` ส่วนจำนวนที่ไม่ใช่ไอเทมใช้หน่วยของ
  ตัวเอง (`คีย์` · `ไฟล์` · `บัญชี` · `ข้อความ`) — เดิมปน `รายการ` (ทัก 13 ก.ย. 2569)
  ด่าน: `tools/_invwords_verify.py` (W4 + W7 negative control)
- **เหตุผลที่ข้ามต้องแยกตามตัวตัดสินจริง** (`_skip_reason` อ้าง `_inv_eligible` ตัวเดียวกับ
  ที่ใช้คัดของ) — เช่น `ข้าม 11 ชิ้น (ฝากไว้แล้ว 8 · หมดอายุแล้ว 2 · ของชั่วคราวที่ฝากไม่ได้ 1)`
  (บอกหน่วย + เลิกวงเล็บซ้อนในวงเล็บ — เดิม `ข้าม 11 (… ของชั่วคราว (ฝากไม่ได้) 1)` อ่านยาก)
  ห้ามเหมารวมเป็น `ฝากไว้แล้ว/หมดอายุ/ไม่อยู่ที่ตัว` และห้ามใส่เหตุที่ไม่มีจริง
  (ฝั่งเบิกเคยขึ้น `ถาวร` — ของถาวรที่ฝากไว้ = เบิกได้ ⇒ เป็นการกล่าวหาผิด)
- **ชิ้นที่ทำไม่สำเร็จต้องมีเหตุที่อ่านรู้เรื่อง** — แปลข้อความเครือข่ายที่รู้จัก
  (`Connection aborted` · `Read timed out` · `Max retries` · DNS · SSL) ด้วยตาราง
  **`NET_FAIL_REASONS` + `err_reason()` ที่ `core/inventory_flow.py` ที่เดียว**
  ข้อความที่ไม่รู้จักให้แสดงของเดิม **ห้ามเดาความหมาย**
  · ฝั่ง "ข้อความที่เว็บตอบเอง" มีตาราง **`WEB_FAIL_REASONS`** ในไฟล์เดียวกัน — เจอจริง
  `ไม่มีแถวที่ถูกแก้ไข` (แถวสถานะ/บัฟในกระเป๋า: `ADDTYPE` · `EXPx5` · `GAIN WEAPON` ฯลฯ)
  ⇒ `เว็บไม่แก้ไขอะไรให้ (ทำรายการนี้ไม่ได้)` (ทัก 13 ก.ย. 2569)
  — ก่อนหน้านี้ตารางฝังอยู่ใน `engine/app_inventory_engine.py` ⇒ ฟีเจอร์อื่น (ไอเทมฟรี ·
  ล็อกอิน) ยังยก exception อังกฤษดิบขึ้นจอ (`('Connection aborted.', RemoteDisconnected(...))`)
  ทั้งหมดถูกส่งผ่าน `err_reason` แล้ว · บรรทัด `! {ไอดี} เหตุผล: …` ของล็อกอินก็เช่นกัน
- **หัวบรรทัดเริ่มทำบอกจำนวนพร้อมกัน ไม่ใช่ `(ต่อบัญชี 10)`** — เขียน `· พร้อมกัน 10 ชิ้น`
  และ **ต้องขึ้นก่อนตัวนับ** — เส้นทางสตรีมยิง op ทันทีที่แต่ละหน้าไหลเข้ามา ยอดเป้าหมาย
  ยังไม่รู้ตอนเริ่ม จึงบอกแค่จำนวนพร้อมกัน แล้วค่อยสรุป `• ไอเทมทั้งหมด X ชิ้น ·
  ฝากได้ Y ชิ้น · ข้าม Z (…)` ตอนดึงครบ (เดิมบรรทัดนี้พิมพ์ตอนงานจบ ⇒ เห็น
  `ฝากแล้ว 1785/1906 ชิ้น (93%)` แล้วค่อยขึ้น `▶ เริ่มเบิก` — ทัก 13 ก.ย. 2569)
- **ปิดเซสชันอัตโนมัติเป็นบรรทัดข้อมูล (`•`) ไม่ใช่ error** — รอบฝาก/เบิกปิดเซสชัน
  อัตโนมัติเสมอ (`auto_close = True`) จึงไม่ใช้ `✗` กับสิ่งที่สำเร็จ
- **ความคืบหน้าต้องเห็นเป็นตัวเลข ทั้งหัวจอและแถวสถานะ** — header ระหว่างรันขึ้น
  `⏳ กำลังฝาก… 620/1,901 ชิ้น (33%) · บัญชีเสร็จ 1/1` และงานยาวจะพิมพ์บรรทัด
  `• [ไอดี] ฝากแล้ว 620/1901 ชิ้น (33%)` ทุก 5 วินาที (ตัวนับ `_RunProgress`)
  — เดิม header บอกแค่ `กำลังฝากไอเทม…` งาน 1900 ชิ้น (35 วิ) จึงดูเหมือนค้าง
- **แถวสถานะของแต่ละไอดีเดินเป็นตัวเลขเรียลไทม์** (`_inv_start_row_progress`) —
  `⏳ เบิก 137/1906 ชิ้น (7%)` ตั้งแต่ `⏳ เบิก กำลังดึงรายการไอเทม…` จนจบ แล้ว **ต้อง
  เรียก `_stop_prog()` ก่อนตั้งสถานะสุดท้าย** ไม่งั้นตัวนับจะทับผลสรุป
  (ผู้ใช้ทัก: ในหน้าสถานะเห็นแต่ `เบิกครบ 68/68` กับ `⏳ กำลังเบิก…` ค้าง ๆ ไม่มี `1/300 2/300`)
  · **ระหว่างที่ยอดเป้าหมายยังไม่นิ่ง** (สตรีมยังดึงหน้าไม่ครบ) ต้องขึ้น
  `⏳ เบิก 68 ชิ้น (กำลังนับรวม…)` — **ห้ามโชว์ `x/y (%)`** เพราะเปอร์เซ็นต์จะ "ลดลงเอง"
  กลางงาน (`3/100` = 3% → `6/391` = 2%) อ่านแล้วเข้าใจผิด (`settled_fn=` ของตัวนับ)
- **ทั้ง 3 เส้นทางของงานชิ้นไอเทมใช้กติกาเดียวกัน** — ฝาก/เบิกทั้งหมด (สตรีม) ·
  เลือกเฉพาะรายการ (สตรีม) · โหมดลบ (path เดิม) ต้องมีตัวนับ + เหตุเป็นไทย + ลองซ้ำเท่ากัน
  (เดิมแก้ที่เส้นทาง "ทั้งหมด" กับ "path เดิม" แล้วตกตัว "เลือกเฉพาะรายการ")
- **ลองซ้ำของชิ้นไอเทม: ทำได้เฉพาะเมื่อ "การเชื่อมต่อขาดกลางทาง"** — `is_transient()`
  ตัดสินจากข้อความจริง · **ถ้าเว็บตอบมาแล้ว (ต่อให้ตอบว่าไม่สำเร็จ) ห้ามส่งซ้ำ** เพราะเว็บ
  ตัดสินไปแล้ว — คนละกติกากับคีย์เวิร์ด/ล็อกอินที่ห้ามส่งซ้ำเสมอ (`ITEM_RETRY_TIMES = 1`
  · `ITEM_RETRY_DELAY_SEC = 0.6` ประกาศที่ `core/inventory_flow.py` ใช้ร่วมกัน)
- **ชิ้นที่พลาดต้องถูก "ตรวจซ้ำอัตโนมัติ" ก่อนสรุป — และต้องตรวจสถานะจริงก่อนยิงซ้ำ**
  (`_inv_retry_round` ในทุกเส้นทางของงานชิ้นไอเทม) ลำดับคือ ① จำชิ้นที่พลาดพร้อม
  ชิ้นข้อมูลจริง ② `find_item_fresh` ดึงสถานะสดของ **เฉพาะชิ้นนั้น** (ค้นด้วยชื่อ +
  ยืนยันด้วย `ItemSerial`) ③ ถ้าสถานะสดบอกว่าทำไปแล้ว = **นับสำเร็จและห้ามยิงซ้ำ**
  (กันทำซ้ำของ เพราะ `PerformItemOperation` ไม่ idempotent) ④ ถ้ายังทำได้จริงจึงยิงซ้ำ
  1 ครั้ง ⑤ ตรวจไม่ได้/ไม่พบในผลค้น **+ รอบแรกเป็นเหตุชั่วคราว (เน็ตสะดุด)** = ไม่เดา
  สถานะ ใช้ข้อมูลเดิมยิงซ้ำแล้วรายงานคำตอบของเว็บตามจริง ⑥ **รอบแรกเว็บตอบมาแล้วว่าไม่ได้**
  (เช่น `ไม่มีแถวที่ถูกแก้ไข`) = **ข้าม ไม่ยิงซ้ำ** — ยิงซ้ำก็ได้คำตอบเดิม แถมได้บรรทัด ✗
  ซ้ำให้อ่านงง (เจอจริง 13 ก.ย. 2569: 5 ชิ้นถูกยิงซ้ำฟรี) และ `is_transient()` ต้องรู้จัก
  **คำแปลไทย** ของเหตุเครือข่ายด้วย ไม่ใช่ดูแต่คำอังกฤษ · โหมดลบ: ชิ้นที่หายจากรายการ =
  ลบไปแล้วตั้งแต่รอบแรก · สรุปท้ายรอบบอก `· ไม่ยิงซ้ำ N ชิ้น` เมื่อมีชิ้นถูกข้าม
  ระหว่างรอบนี้แถวสถานะ + หัวจอเดินเป็นตัวเลขของรอบตรวจซ้ำ (`header_note`) ไม่ค้างที่ 100%
- **รายงานต้องบอกว่าอันไหน "สำเร็จจริง"** — สรุปท้ายรอบขึ้นบรรทัด
  `■ ตรวจซ้ำอัตโนมัติ  ยิงซ้ำแล้วสำเร็จเพิ่ม N ชิ้น · ตรวจสถานะแล้วทำไปแล้วตั้งแต่รอบแรก M ชิ้น`
  ตามด้วย `✓ สำเร็จจริง: <ชื่อชิ้น…>` (ฝั่งการ์ดสรุปใช้ `🔄 ตรวจซ้ำอัตโนมัติ: สำเร็จเพิ่ม N ชิ้น`)
  และยอด `พลาด N ชิ้น` ทุกบรรทัดต้องเป็นยอด **หลัง** รอบตรวจซ้ำ (ชิ้นที่กู้คืนได้ถูกตัดออก)
- **การปิดเซสชันไม่ใช่ความผิดพลาด** — ทั้งกรณีสำเร็จและกรณี "ไม่มีเซสชันค้าง" ใช้ `•`
  (`• [{ไอดี}] ยังไม่มีเซสชันค้างให้ปิด (ข้าม)`) ห้ามใช้ `✗` และทางเดินของคำสั่งรวมที่ไม่มี
  ผู้เรียกแล้ว (ปุ่มที่ถอดไป) ถูกลบทั้ง block — ไม่เหลือข้อความ ✗ ค้างในซอร์ส
- **แท็บฝาก/เบิกไม่มีปุ่มปิดเซสชันเอง** — ถอดออกตามคำสั่ง (ปุ่มกดไม่ได้จริง เพราะ
  sessions ถูกปิดหลังจบรอบทุกครั้ง) `_inv_close_sessions` ถูกถอดทั้ง entry point
  ส่วน `_inv_close_sessions_for` ยังใช้ตอนลบไอดีออกจากตาราง
- **`■ เวลารวม` ใช้ `_fmt_sec` ตัวเดียวกับ `ใช้เวลา`** ของล็อกอิน (ใต้ 1 นาทีเป็น `6.1วิ`)
- **`ใช้เวลา` ของรอบต้องบวกกันได้ — ห้ามมีเวลาแอบแฝง** — ก่อนเริ่มรอบ แอป GET หน้า Keyword
  หนึ่งครั้งเพื่อเช็คว่าเว็บปิดปรับปรุงไหม ซึ่งอยู่ *ก่อน* นาฬิกาของแต่ละบัญชี ⇒ เดิมเวลาส่วนนี้
  หายเงียบ ๆ ทำให้ `■ ล็อกอิน N/N บัญชี · ใช้เวลา 3.8วิ` มากกว่าผลรวมขั้นของบัญชี (3.3วิ)
  โดยไม่มีคำอธิบาย (ผู้ใช้ทัก 13 ก.ย. 2569 "ทำไมไม่เหมือนกัน") ⇒ พิมพ์บรรทัด
  `   ตรวจเว็บก่อนเริ่ม Xวิ` ให้เห็น (วัดจริง 0.43–0.54 วิ/รอบ) แล้ว "ใช้เวลา" = เวลาตรวจเว็บ +
  เวลาของงาน (บัญชีที่ช้าสุดเมื่อรันขนาน) · ใช้ที่เดียว `_website_down_or_log` จึงครอบทั้ง
  flow ล็อกอิน · กรอกคีย์เวิร์ด · รันอัตโนมัติ · ด่าน: `tools/_speed_verify.py` T10
- **ห้ามยิงหน้า Keyword เต็มหน้าซ้ำทุกรอบเพื่อเช็คปิดปรับปรุง** — วัดจริง 0.405–0.500 วิ/ครั้ง
  ทั้งที่รอบเร็วสุดของผู้ใช้ใช้แค่ 0.6 วิ ⇒ `check_website_maintenance_info()` **จำคำตอบไว้ใช้ซ้ำ**
  (`MAINT_OK_TTL_SEC` 120 วิ สำหรับ "เว็บปกติ" · `MAINT_DOWN_TTL_SEC` 30 วิ สำหรับ "ปิดปรับปรุง" —
  เว็บล่มไม่ต้องยิงถี่ แต่กลับมาแล้วรู้ไว) · `force=True` สำหรับบังคับเช็คใหม่ · **หลักฐานฟรี**:
  `session_is_valid` ที่โหลดหน้า Keyword อยู่แล้วเรียก `note_website_seen()` ⇒ ระหว่างรอบคำตอบสด
  เอง รอบถัดไปยิงเช็คซ้ำ 0 ครั้ง · log บอกตามจริง (`   ตรวจเว็บก่อนเริ่ม 0.4วิ` = เช็คใหม่ ·
  `   ตรวจเว็บก่อนเริ่ม: ใช้ผลเดิม (เช็คล่าสุด 12วิก่อน)` = ไม่เสียเวลา)
- **ปิดความเสี่ยง "คำตอบเก่า" แล้ว** — คำตอบที่จำไว้ **ห้ามเป็นคำตอบสุดท้ายแบบเงียบ ๆ**:
  `MAINT_PROOF_SEC` 20 วิ = หลักฐานสด (เช็คจริง/โหลดหน้าจริงสำเร็จภายใน 20 วิ) ⇒ ไม่ยืนยันซ้ำ ·

## ป้าย "เว็บไม่ยืนยันผล" ต้องเป็นทางสุดท้ายจริง ๆ — ใช้คำพูดของเว็บก่อนเสมอ

หลักฐาน (log + ภาพหน้าจอผู้ใช้ 13 ก.ย. 2569): 23 บัญชีขึ้นป้ายกว้าง
`✗ <id>  1j322hfw  เว็บไม่ยืนยันผล` ทั้งที่เว็บเด้งกล่องของมันเองว่า

ลำดับการอ่านเหตุผล (บังคับ — ตรงตามนี้เท่านั้น)

1. **กล่องข้อความของเว็บ (`alert`)** — คำพูดของเว็บเอง อ่านจาก**ทุก part** ของ delta
   ไม่จำกัดชนิด (เดิมอ่านเฉพาะ `scriptBlock`/`scriptStartupBlock` ⇒ ข้อความหลุด)
2. **ข้อความที่เว็บเขียนบนหน้า** — เทียบแบบทน tag/ช่องว่าง และสแกน**ทุก part**
   ไม่ใช่แค่ `ItemPanel` (เว็บมักคั่นคำไทยด้วย tag เช่น `คีย์เวิร์ดนี้</span>ไปแล้ว`)

4. **ป้ายตรงไปตรงมา** `เว็บไม่ยืนยันผล` + เก็บคำตอบดิบไว้ที่
   `<LOG_DIR>/kwdump_<code>_<เวลา>.html` (ครั้งเดียวต่อคีย์ต่อรอบรัน) เพื่อให้รู้ของจริง
   แล้วค่อยเพิ่มเกณฑ์ — ไม่เดา

  (`คียเวิร์ด` ขาดไม้ทัณฑฆาต) ⇒ กฎ "คีย์ถูกใช้ไปแล้ว" ไม่เคยแมตช์ข้อความจริงของเว็บเลย
  และผู้ใช้เห็นข้อความดิบยาว ๆ แทนเหตุสั้น

  หลายรูป (เจอจริง 13 ก.ย. 2569 16:34: `คุณได้รับคียเวิร์ดนี้ไปแล้ว` ขาดไม้ทัณฑฆาต)
  ⇒ `_match_short_reason` เทียบด้วย `_fold_marks()` (ตัดเครื่องหมายไทยทั้งสองฝั่ง)

## ทีมอาการเดียวกัน — ข้อความระบบดิบ / สถานะไม่เดิน / คำไม่ตรงกัน

ตรวจทั้งระบบ 13 ก.ย. 2569 แล้วพบอาการชนิดเดียวกันกระจายอยู่หลายฟีเจอร์ (ไม่ใช่แค่ที่ผู้ใช้ทัก)
กติกาที่วางไว้เพื่อไม่ให้กลับมา

- **ข้อความ exception ดิบต้องไม่ถึงตาผู้ใช้ทุกฟีเจอร์** — ทุกที่ที่พิมพ์ `{e}` / `{err}` /
  `{exc}` ต้องผ่าน `err_reason()` ก่อน (รู้จักคำนั้น = แปล · ไม่รู้จัก = แสดงของเดิม)
  จุดที่พบและแก้: `app_inventory_engine` (12 บรรทัด `✗ [ไอดี] …`) ·
  `app_autoitem_engine` (`ดึงคีย์ไม่สำเร็จ` · ผลลัพธ์ที่ไม่สำเร็จ · `ล็อกอินไม่สำเร็จ — …`) ·
  `app_login_flow_core` (บรรทัด `! {ไอดี} เหตุผล: …`)
- **ตารางเหตุเป็นไทยมีที่เดียว** — `core/inventory_flow.py` (`NET_FAIL_REASONS` ·
  `err_reason` · `is_transient` · `ITEM_RETRY_TIMES`) `app_inventory_engine` เก็บ
  `_op_fail_reason`/`_op_is_transient` เป็น alias เพื่อความเข้ากันได้ แต่ **ห้ามมีสำเนาตาราง**
- **บรรทัด "รายงานของรอบ" ไม่ใช่ "ความผิดพลาด"** — `_log_category()` ต้องคืน
  `summary`/`warn` ให้บรรทัดที่เริ่มด้วย `■` · `🔄` · `! [{ไอดี}]` ก่อนไปดูคำในข้อความ
  เดิมบรรทัด `🔄 … ตรวจซ้ำเสร็จ · สำเร็จเพิ่ม 0 ชิ้น · ยังไม่สำเร็จ 5 ชิ้น` (บรรทัดสรุป)
  ถูกเขียนลง `error_*.log` เป็น ERROR เพราะมีคำว่า `ไม่สำเร็จ` อยู่ข้างใน (ทัก 13 ก.ย. 2569)
  ด่าน: `tools/_invretry_verify.py` R13a–R13d (รวม control ว่าบรรทัดล้มเหลวจริงยังเป็นแดง)
- **จำนวนคีย์เวิร์ดใช้ `อัน`** — `• เพิ่มคีย์เวิร์ด #3 (รวม 3 อัน)` · `• ลบคีย์เวิร์ด (เหลือ 2 อัน)`
  ให้ตรงกับที่อื่นในโปรแกรม (`กรุณาใส่คีย์เวิร์ดอย่างน้อย 1 อัน`) — เดิมใช้ `รายการ`
- **หน่วยของตัวเลขต้องตรงกันทั้งไฟล์** — งานชิ้นไอเทมใช้ `ชิ้น` ทั้งหมด (เดิมทางโหมดลบ
  ยังใช้ `รายการ` ปน) และการ์ดสรุปใช้ `ชิ้นที่…ไม่สำเร็จ` ไม่ใช่ `รายการที่…ไม่สำเร็จ`
- **หลักการ**: ตรวจให้ครบ *ชนิด* ของอาการ ไม่ใช่แก้เฉพาะจุดที่ผู้ใช้ส่งภาพมา — อาการหนึ่ง
  มักมีรอยเดิมอยู่หลายฟีเจอร์

### ความทนทานที่พบเพิ่มจากการไล่ทั้งระบบ (ชนิดเดียวกัน)

- **เธรดต่อบัญชีต้องมีด่าน exception** (`_worker` ของรอบฝาก/เบิก) — เดิมถ้า
  `_inv_account_round` โยน exception เธรดตายเงียบ: ตัวนับบัญชีไม่เดิน และบัญชีนั้น
  **หายจากผลสรุป**ทั้งที่ผู้ใช้ติ๊กไว้ ⇒ ตอนนี้จับเป็นบัญชี `พลาดบางส่วน` + แถวสถานะ
  ขึ้น `✗ ผิดพลาด · <เหตุ>` และยังนับ `account_done()` ตามปกติ
- **`f.result()` ถูกครอบ try** (โหมดลบ) — ชิ้นเดียวพังไม่ล้มทั้งบัญชี
- **ชิ้นที่ถูกยกเลิกก็นับเข้าตัวนับรวม** — กดหยุดแล้วตัวเลขความคืบหน้าไม่ค้างต่ำกว่ายอดจริง
- **`chosen` ต้องกันไอดีซ้ำ** — เส้นทางเลือกเฉพาะรายการเดิมสร้าง `acc_tuples` จากรายการดิบ

  ⇒ ตอนนี้ข้ามพร้อมแจ้ง `ข้ามไอดีซ้ำ N ไอดี`
- **"⏳ กำลังทำงาน" ตั้งเฉพาะแถวที่เข้ารอบ** — แถวที่ไม่ได้ติ๊กต้องไม่ขึ้นว่ากำลังทำงาน
- **ไฟล์คุกกี้เขียนแบบ atomic** (tmp + fsync + `os.replace`) — ไฟล์สถานะอื่นทำแบบนี้

  ⇒ โปรแกรมตายกลางคันทำให้คุกกี้พังทั้งไฟล์ (ต้องล็อกอินใหม่ทุกบัญชี)
